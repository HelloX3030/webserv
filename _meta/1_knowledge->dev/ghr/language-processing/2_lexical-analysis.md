# lexical analysis


## essence

```
character stream → token stream
```

the lexer (also: tokeniser, scanner) transforms a linear sequence
of characters into a linear sequence of tokens.

a **token** is the smallest unit of meaning in the language.
characters have no meaning — they are just bytes.
tokens carry categorical identity: "this is an identifier",
"this is a number", "this is an opening brace".


---


## what a token is

a token is a pair: (type, value).

```
type:   categorical identity — what kind of thing this is
value:  lexeme — the actual character sequence from the source
```

example — tokenising `listen 8080;`:

```
characters:  l i s t e n   8 0 8 0 ;
                 ↓
tokens:      (STRING, "listen")  (STRING, "8080")  (SEMICOLON, ";")
```

the lexer does not know that "listen" is a directive name
or that "8080" is a port number. it knows only that both
are sequences of non-whitespace, non-structural characters.

meaning comes later. the lexer provides category, not semantics.


---


## why tokenisation is a separate phase

2 reasons: formal and practical.

formal:
    tokenisation handles regular structure.
    parsing handles context-free structure.
    these are different language classes with different automata.
    conflating them loses the computational separation.

practical:
    the parser operates on tokens, not characters.
    without tokenisation, the parser must handle:
    - whitespace (spaces, tabs, newlines)
    - comments
    - character-level ambiguity (is "if" a keyword or identifier start?)

    these concerns pollute every grammar production.
    tokenisation eliminates them once, at the boundary.


---


## the regular language connection

token patterns are regular languages.

an identifier: letter followed by letters or digits.
    regex: [a-zA-Z][a-zA-Z0-9]*

a number: one or more digits.
    regex: [0-9]+

a string literal: quote, non-quotes, quote.
    regex: "[^"]*"

these patterns require no memory beyond "what state am I in?"
finite automata suffice. recognition is O(n).

the lexer is a **deterministic finite automaton** (DFA).
each state represents "what have I seen so far?"
each transition represents "given this character, go to that state."
accepting states represent "this is a complete token of type X."


---


## maximal munch

when multiple token patterns could match, which wins?

the **maximal munch** rule: take the longest match.

```
input:  "iffy"
```

both "if" (keyword) and "iffy" (identifier) start at position 0.
maximal munch selects "iffy" — the longer match.

this is why keywords are not reserved at the character level.
"if" is a keyword only when followed by non-identifier characters.
"iffy" is an identifier because the match extends further.

lexer generators (lex, flex) implement maximal munch automatically.
hand-written lexers must implement it explicitly.


---


## what the lexer does not do

the lexer does not:
- validate values (is "99999" a valid port?)
- interpret values (what number does "8080" represent?)
- understand context (is "root" a directive or a path?)
- check structure (are braces balanced?)

these belong to later phases.

the lexer's contract: segment characters into tokens,
annotate each with a type, record source location for errors.
nothing more.


---


## line number tracking

every token carries its source line number.

this is the **only mechanism** for precise error messages in later phases.
once tokenisation completes, character positions are gone.
the parser sees tokens, not characters.

if the parser reports "unexpected token", it needs to say where.
the line number on the token provides "where".

this is why comment stripping (if done at read time) must preserve
line structure — replace comment characters with spaces, not delete them.

## token types: design considerations

how many token types?

minimalist approach (ConfigFrontend):
```
STRING      — any non-structural character sequence
LBRACE      — {
RBRACE      — }
SEMICOLON   — ;
END         — sentinel for stream exhaustion
```

the lexer makes no semantic distinctions.
"listen", "8080", "/var/www" are all STRING.
the parser distinguishes them by position in the grammar.

maximalist approach (typical programming language):
```
IDENTIFIER, INTEGER, FLOAT, STRING_LITERAL,
KEYWORD_IF, KEYWORD_ELSE, KEYWORD_WHILE, ...
PLUS, MINUS, STAR, SLASH, ...
LPAREN, RPAREN, LBRACE, RBRACE, ...
```

the lexer makes fine-grained distinctions.
the parser receives pre-classified tokens.

trade-off:
- minimalist: lexer is trivial, parser does more work
- maximalist: lexer is complex, parser is simpler

neither is universally correct. the choice depends on
the language's complexity and the desired separation of concerns.

## implementation patterns

table-driven DFA:
    transition table indexed by (state, character).
    generated by lexer generators (lex, flex, re2c).
    fastest possible: one table lookup per character.

hand-written loop:
    switch on current character.
    accumulate into buffer.
    emit token when pattern completes.
    simpler to understand, adequate for simple languages.

the ConfigFrontend uses hand-written loop:
    4 token types, no complex patterns, no regex needed.
    a table-driven DFA would be overengineering.

## in other languages

Haskell (using Alex lexer generator):
```haskell
tokens :-
    $white+                 ;
    "server"                { \_ -> TServer }
    "{"                     { \_ -> TLBrace }
    "}"                     { \_ -> TRBrace }
    ";"                     { \_ -> TSemi }
    [a-zA-Z0-9\/\.\-\_]+    { \s -> TString s }
```

Rust (hand-written, typical pattern):
```rust
fn next_token(&mut self) -> Token {
    self.skip_whitespace();
    match self.peek_char() {
        Some('{') => { self.advance(); Token::LBrace }
        Some('}') => { self.advance(); Token::RBrace }
        Some(';') => { self.advance(); Token::Semicolon }
        Some(_)   => self.scan_string(),
        None      => Token::End,
    }
}
```

Agda (dependently typed, lexer as proof):
```agda
-- token type indexed by the regular language it matches
data Token : RegExp → Set where
  TString : (s : String) → Matches stringPattern s → Token stringPattern
  TLBrace : Token (char '{')
  ...
```

in Agda, the token type can carry a proof that the lexeme
matches the pattern — the type system enforces lexer correctness.


---


## summary

lexical analysis:
- transforms characters to tokens
- handles regular structure (patterns without nesting)
- uses finite automata (DFA)
- O(n) time, O(1) space beyond input
- records line numbers for error reporting
- makes no semantic judgments

the lexer is the boundary between bytes and meaning.
everything before is I/O. everything after is language.
